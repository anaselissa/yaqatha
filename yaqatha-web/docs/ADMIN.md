# بنية لوحة الإدارة (للتنفيذ لاحقًا)

لا يُبنى شيء شكلي: كل عملية أدناه **موجودة في القاعدة ومُختبَرة** عبر REST/RPC بصلاحيات المحرر أو المدير (`tests/admin-api.test.mjs` + `yaqatha-db/tests/db.test.sql`). ما بقي هو الواجهة فقط.

## 1. المبادئ المعمارية (قرارات)

1. **لا مفتاح خدمة.** اللوحة تعمل بجلسة الموظف نفسها (نفس كوكيز `/login`) وتمرّ كل عملية بـRLS. *السبب: سرّ واحد مسرَّب لا يفتح القاعدة كلها.*
2. **مسار `/admin` خادمي (SSR).** يتحقق middleware من الدور عبر قراءة `staff_roles` للمستخدم الحالي؛ وغير الموظف يرى 404 لا 403. التحقق الحقيقي يبقى في القاعدة (RLS + `require_staff()`)، والواجهة لا تُعتمد.
3. **نماذج POST عادية** مثل بقية الموقع (فحص Origin + PRG)، ولا JavaScript إلا للسحب والإفلات (مع أزرار «حرّك لأعلى/لأسفل» للوحة المفاتيح).
4. **المعاينة بصلاحية الموظف:** صفحات `/admin/preview/*` تعيد استخدام مكوّنات الصفحات العامة، لكنها تقرأ بـJWT الموظف فتظهر المسودات (RLS تسمح للفريق بكل الحالات)، وترسل `noindex` و`no-store`.
5. **التعارض في التعديل المتزامن:** `PATCH ... ?updated_at=eq.<القيمة التي فتحها المحرر>`؛ إن أعاد `[]` فقد عدّلها غيره (مُختبَر). لا إضافات على القاعدة.
6. **كل تغيير يُسجَّل تلقائيًا** في `audit_log` بمشغّلات القاعدة؛ لا تسجيل في الواجهة.

## 2. العمليات وما يقابلها

| الوظيفة (وثيقة التدفقات) | الواجهة تستدعي | الحماية في القاعدة |
|---|---|---|
| A0 دخول الموظف / عرض الدور | `GET staff_roles` (صفّه فقط) | RLS: يرى صفه؛ المدير يرى الجميع |
| A1 إضافة/تعديل مادة | `POST/PATCH materials` + `material_domains/topics/needs` | مشغّل شروط النشر (محتوى، مصدر، ربط) |
| A2 إخفاء/إظهار/أرشفة | `PATCH materials {status}` | بلا حذف (لا صلاحية DELETE) |
| A2 أثر الإخفاء قبل التأكيد | `rpc material_impact` | أعداد فقط بلا هويات |
| المراجعة (تجريبية…معتمدة) | `PATCH content_review` | جدول منفصل لا يراه الجمهور |
| A3 إنشاء مسار وإصدار 1 | `POST paths`، `POST path_versions` | الحالة لا تُكتب مباشرة (منح أعمدة)، ورقم الإصدار تلقائي |
| A3 إضافة/تعديل/حذف خطوة (مسودة) | `POST/PATCH/DELETE steps`، `step_materials` | مشغّل يمنع تغيير غير المسودة |
| A3 **إعادة الترتيب** | `rpc reorder_steps` (هجرة 7) | معاملة واحدة، مسودة فقط |

| A6 المجالات/الاحتياجات/الموضوعات | `POST/PATCH domains|topics|needs` + `need_topics` | لا حذف؛ إخفاء فقط؛ تحويلات الروابط تلقائية |
| A7 الرئيسية | `POST/DELETE homepage_items` | يختفي العنصر تلقائيًا إن أُخفي هدفه |
| A8 الفريق | `POST staff_invites`، `PATCH/DELETE staff_roles` (مدير) | حماية آخر مدير؛ الدعوة تُفعَّل عند أول دخول |
| A9 سجل التغييرات | `GET audit_log` (مدير) | بلا نصوص كاملة (`text_changed` فقط) |
| بلاغات المواد | `GET/PATCH material_reports` | المبلِّغ يرى بلاغه فقط |

## 3. الشاشات المقترحة بترتيب البناء

1. **حارس `/admin` + الدور + قائمة المواد** (أصغر شريحة تعمل فعليًا: إخفاء مادة بنقرتين). *الأولوية لأن الإخفاء السريع متطلب أمانة علمية.*
2. محرر المادة + المعاينة + البلاغات.
3. المسارات: القائمة، محرر الإصدار والخطوات (مع إعادة الترتيب)، النشر، الإصدار الجديد، السحب.
4. التصنيفات + لوحة التغطية (احتياجات منشورة بلا محتوى).
5. الرئيسية، ثم الفريق وسجل التغييرات (مدير فقط).

## 4. ما ينبغي ألا يتغير

- لا DELETE لمادة أو مسار أو تصنيف: يبقى الإخفاء والأرشفة.
- لا تعديل لـ`status` إصدار إلا عبر RPC.
- لا استخدام لمفتاح الخدمة في أي مرحلة، ولا في Edge Functions إلا إن ظهرت حاجة لا تُحل بما سبق (ولم تظهر).

## 5. فجوات معروفة (ليست حاجزة)

- **تفعيل الدعوات يتطلب بريدًا مؤكَّدًا** في `auth.users` (Google يضمنه). إن ظهرت حالة لا تُطبَّق فيها الدعوة تلقائيًا فالواجهة تستدعي `rpc claim_staff_invite` بعد الدخول.
- **إعادة إدراج إصدار مسحوب (`withdrawn → retired`)** مسموحة في مشغّل الحالات لكن بلا RPC؛ تُضاف دالة صغيرة عند الحاجة لها.
