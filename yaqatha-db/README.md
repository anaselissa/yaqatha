## التشغيل والاختبار

```bash
tests/run.sh        # يعيد إنشاء قاعدة yq_test، يطبّق كل شيء، ثم يشغّل الاختبارات
```
يتطلب PostgreSQL 15+ (عروض `security_invoker`). على Supabase: طبّق ملفات `migrations` بالترتيب ثم `seed.sql`
(لا تطبّق `tests/stub_supabase.sql`؛ هو بديل لمخطط `auth` للاختبار المحلي فقط).

## نموذج الأمان

- **كل جدول عليه RLS**، وكل المنح صريحة (تُسحب منح Supabase الافتراضية في الهجرة 5).
- **الزائر (anon):** يقرأ المنشور فقط. لا يصل إلى أي جدول للمستخدم أو الإدارة.
- **المستخدم:** يقرأ بياناته فقط. الأهداف تُكتب مباشرة (RLS)، أما **التسجيل في المسارات وحالة الخطوات فعبر RPC فقط**
  (`start_path`, `set_step_state`, `migrate_enrollment`, …) لأن الثبات على الإصدار قاعدة جوهرية لا تُترك للعميل.
- **الفريق:** `editor` و`manager` عبر جدول `staff_roles`. حالة الإصدار لا تُعدَّل مباشرة (منح أعمدة)؛ تُغيَّر عبر
  `publish_path_version` و`withdraw_version`. لا حذف للمواد ولا للمسارات ولا للتصنيفات.
- **عدم كشف المحررين:** جداول المحتوى العام بلا `created_by`؛ المؤلف في `audit_log` (للمدير فقط).
- حالة المراجعة والملاحظة الداخلية في `content_review` (للفريق فقط، لا تُعرض للجمهور).

## الإجراءات (RPC)

| المستخدم | الفريق |
|---|---|
| `start_path(path_id)` — متكافئة | `create_draft_version(path_id)` — ينسخ مع المعرّفات الثابتة للخطوات |
| `set_step_state(enrollment, step, state)` | `publish_path_version(version, changelog)` — الملخص إلزامي بعد الإصدار 1 |
| `mark_step_opened(enrollment, step)` | `withdraw_version(version, note)` — يوقف البدء الجديد تلقائيًا إن كان المنشور |
| `plan_migration` / `migrate_enrollment` — ذرّية ومتكافئة | `material_impact(material)` — أعداد فقط |
| `restart_enrollment` / `archive_enrollment` / `restore_goal` | `claim_staff_invite()` — لمن لم تُطبَّق دعوته تلقائيًا |

`search_content(q)` و`paths_current` و`enrollment_progress` للقراءة.

## قرارات اتُّخذت أثناء التنفيذ (كانت أسئلة مفتوحة)

1. **تعديل الإصدار المنشور (A4):** نُفّذ الخيار «ب». بنية الإصدار المنشور مجمّدة بالمشغّلات (لا إضافة/حذف/ترتيب/تغيير نوع)،
   ويُسمح بتصحيح نص عنوان الخطوة وتعليماتها واستبدال مادة بأخرى، مع تسجيلها في `audit_log`. للتحول إلى الخيار «أ» احذف
   الاستثناءين في `steps_guard` و`step_materials_guard`.
2. **إجابات التمارين:** لا تُخزَّن (لا جدول لها). إضافتها لاحقًا جدول جديد بسياسة مالك فقط دون المساس بالموجود.
3. **حدود:** عنوان الهدف 120 حرفًا، وصفه 2000، وعدد الأهداف 100 للمستخدم، وبلاغ المادة 1000.
4. **الدعوات:** تُطبَّق تلقائيًا عند إنشاء المستخدم إن كان بريده مؤكدًا، وإلا عبر `claim_staff_invite()` بعد التأكيد.
5. **أول مدير:** يُدرج يدويًا في `staff_roles` (`role = 'manager'`) بمفتاح الخدمة.

## ما اختُبر وما لم يُختبر

**اختُبر فعليًا (PostgreSQL 16، بديل لمخطط auth):** عزل المستخدمين، منع الكتابة غير المصرّح بها، شروط نشر المواد، الإخفاء دون حذف،
تحويلات الروابط ومنع إعادة استخدامها، ثبات التقدم عند إصدار جديد، الانتقال والتكافؤ والذرّية، «ابدأ من جديد»، سحب الإصدار،
الأهداف (أرشفة/استعادة/حد/تكافؤ)، البحث العربي (تشكيل، «ال»، همزات، بادئة، حقن)، الدعوات وحماية آخر مدير،
سجل التغييرات، حذف الحساب، وسلامة المفاتيح الأجنبية.

**لم يُختبر بعد (يتطلب مشروع Supabase حقيقيًا):**
- تدفق Google OAuth الفعلي وسلوك `auth.users` الحقيقي (الأعمدة والمشغّل `on_auth_user_created`).
- أداء الاستعلامات على بيانات كبيرة (الفهارس موضوعة، لكن لم تُقس).
- جودة البحث العربي على محتوى حقيقي؛ PostgreSQL لا يوفّر تجذيرًا عربيًا هنا، والتطبيع خفيف عمدًا.
- أي هجرة مستقبلية ينشئ جداول جديدة تحصل على منح Supabase الافتراضية: أضف دائمًا `enable row level security` و`revoke` صريحًا.
